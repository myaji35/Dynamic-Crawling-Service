# DCS (동적 크롤링 서비스) 헌법

## 핵심 원칙

### I. 사용자 중심의 단순성 (NON-NEGOTIABLE)

AI 챗봇 기반의 대화형 인터페이스를 통해 비개발자도 크롤링 프로젝트를 생성하고 관리할 수 있어야 합니다.

**규칙:**

- 모든 설정은 자연어 대화를 통해 구성 가능해야 함
- CSS Selector, Cron 표현식 등 기술 용어는 사용자에게 직접 노출하지 않음
- 챗봇은 기술 설정을 자동으로 추천하고, 사용자는 확인만 수행
- 샘플 데이터를 통한 검증 후 확정하는 방식으로 설정 오류 최소화

**이유:**
비개발자가 복잡한 크롤링 작업을 수행할 수 있게 하는 것이 DCS의 핵심 가치입니다. 기술적 복잡성을 AI가 흡수하여 사용자 경험을 극대화합니다.

### II. 프로젝트별 동적 스키마 지원

각 크롤링 프로젝트는 독립적이고 유연한 데이터 구조를 가져야 합니다.

**규칙:**

- 프로젝트마다 다른 데이터 스키마(컬럼)를 정의할 수 있어야 함
- NoSQL 또는 스키마리스 데이터베이스(Firestore, BigQuery 등) 사용
- 모든 수집 데이터는 projectId와 run_timestamp 메타데이터 포함
- 새로운 필드 추가/삭제가 기존 프로젝트에 영향을 주지 않아야 함

**이유:**
범용 크롤링 서비스는 다양한 도메인의 데이터를 수집해야 하므로, 고정된 스키마로는 요구사항을 충족할 수 없습니다.

### III. AI 기반 자동화

AI는 사용자 의도를 분석하여 기술 설정을 자동으로 생성하고 최적화해야 합니다.

**규칙:**

- HTML 구조 분석을 통한 CSS Selector 자동 추천
- 사용자가 입력한 필드명(예: "기관명", "주소")을 기반으로 가장 적합한 셀렉터 제안
- 추천된 설정으로 샘플 크롤링을 실행하여 검증
- 크롤링 실패 시 자동 재시도 및 에러 패턴 학습

**이유:**
AI를 통한 자동화가 없다면 사용자는 여전히 기술적 지식을 요구받게 되어 DCS의 핵심 가치가 훼손됩니다.

### IV. 확장성, 안정성 및 다양한 실행 환경 지원 (NON-NEGOTIABLE)

대규모 분산 크롤링을 안정적으로 처리할 수 있는 아키텍처를 유지하며, 서버리스와 데몬 환경 모두에서 안정적으로 운영되어야 합니다.

**규칙:**

- **서버리스 환경**: GCP Cloud Run/Functions를 통한 수평적 확장 지원
- **데몬 환경**: 장시간 실행되는 백그라운드 프로세스로 안정적 운영
  - 프로세스 크래시 시 자동 재시작 메커니즘 (systemd, supervisor, PM2 등)
  - Graceful shutdown 지원 (진행 중인 작업 완료 후 종료)
  - 리소스 누수 방지 (메모리 관리, 연결 풀 정리)
- Cloud Pub/Sub를 활용한 작업 큐 분산 처리
- 특정 프로젝트의 실패가 다른 프로젝트에 영향을 주지 않는 격리 보장
- 256개 이상의 동시 작업을 처리할 수 있는 성능 유지
- 다양한 크롤링 시나리오 지원:
  - 정적 HTML 페이지
  - JavaScript 렌더링 필요 페이지 (SPA)
  - 인증이 필요한 페이지
  - API 기반 데이터 수집
  - 파일 다운로드 (PDF, CSV 등)

**이유:**
실제 사용 사례(예: 256개 지자체 데이터 수집)를 고려할 때, 단일 인스턴스 기반 아키텍처로는 요구사항을 충족할 수 없습니다. 또한 데몬 환경에서 장시간 안정적으로 운영되기 위해서는 프로세스 관리, 리소스 관리, 에러 복구 메커니ズ�이 필수적입니다.

### V. 관찰 가능성(Observability) 및 데몬 모니터링

모든 크롤링 작업의 상태와 결과는 실시간으로 추적 가능해야 하며, 데몬 프로세스의 헬스 체크가 가능해야 합니다.

**규칙:**

- 대시보드를 통한 프로젝트별 실행 현황 시각화
- 성공/실패/대기 상태의 명확한 표시
- 에러 발생 시 상세 로그와 함께 재시도 옵션 제공
- 최근 수집 데이터 샘플 뷰어 제공
- 구조화된 로깅(Structured Logging) 필수
- **데몬 프로세스 모니터링**:
  - Health check endpoint 제공 (HTTP 또는 파일 기반)
  - 프로세스 uptime 추적
  - 메모리 사용량, CPU 사용률 모니터링
  - 작업 큐 길이 및 처리 속도 메트릭
  - Dead letter queue 모니터링 (반복 실패 작업)

**이유:**
비동기로 실행되는 크롤링 작업의 특성상, 사용자가 현재 상태를 파악하고 문제를 진단할 수 있어야 서비스 신뢰도가 유지됩니다. 데몬 환경에서는 프로세스 자체의 헬스 상태 모니터링이 운영 안정성의 핵심입니다.

## 기술 제약사항

### 클라우드 플랫폼

- **필수**: Google Cloud Platform (GCP)
- **스케줄링**: Cloud Scheduler
- **작업 큐**: Cloud Pub/Sub
- **실행 환경**: Cloud Run 또는 Cloud Functions (서버리스) 또는 Compute Engine (데몬)
- **데이터 저장**: Firestore 또는 BigQuery

**이유**: GCP의 서버리스 아키텍처는 비용 효율적이고 자동 확장이 가능하여 DCS의 요구사항에 최적화되어 있습니다.

### 크롤링 엔진

- **지원 도구**: Puppeteer, Playwright 등 헤드리스 브라우저
- **동적 콘텐츠 지원 필수**: JavaScript로 렌더링되는 페이지 처리 가능
- **타임아웃 설정**: 페이지 로드 실패 시 명확한 에러 메시지와 함께 실패 처리
- **다양한 크롤링 전략 지원**:
  - HTML 파싱 (Cheerio, BeautifulSoup 등 경량 파서)
  - 브라우저 자동화 (Puppeteer, Playwright)
  - API 호출 (axios, fetch)
  - 프로젝트 특성에 따라 적절한 도구 자동 선택

### 데몬 환경 운영 요구사항

- **프로세스 관리**: systemd, supervisor, PM2 등을 통한 프로세스 관리
- **재시작 정책**: 크래시 발생 시 자동 재시작, 연속 실패 시 백오프 정책
- **로그 로테이션**: 로그 파일 크기 제한 및 자동 순환
- **환경 변수 관리**: 민감한 정보는 환경 변수 또는 Secret Manager 사용
- **Signal 처리**: SIGTERM, SIGINT 등 종료 시그널 처리를 통한 Graceful shutdown
- **PID 파일 관리**: 중복 실행 방지를 위한 PID 파일 관리

### 보안

- **사용자별 데이터 격리**: 프로젝트 접근 권한 엄격히 관리
- **API 키 기반 인증**: 데이터 제공 API는 사용자별 API 키로 보호
- **민감 정보 보호**: 크롤링 설정에 포함된 URL, 인증 정보 암호화 저장

## 품질 기준

### 성능 목표

- **동시 작업 처리**: 최소 256개 이상의 동시 크롤링 작업
- **응답 시간**: 대시보드 조회 < 2초
- **샘플 크롤링 실행**: < 10초 (단일 페이지 기준)

### 사용자 경험

- **프로젝트 생성 시간**: 챗봇을 통한 전체 설정 프로세스 < 5분
- **에러 복구**: 크롤링 실패 시 사용자에게 이해 가능한 에러 메시지 제공
- **데이터 확인**: 샘플 크롤링 결과를 통한 설정 검증 필수

### 안정성

- **개별 작업 격리**: 단일 작업 실패가 시스템 전체에 영향을 주지 않음
- **자동 재시도**: 일시적 네트워크 오류 등에 대한 재시도 메커니즘
- **모니터링**: 모든 크롤링 작업의 성공률 추적 (목표: 95% 이상)

### 데몬 안정성 목표

- **Uptime**: 99.9% 이상 (월간 최대 43분 다운타임)
- **메모리 안정성**: 24시간 이상 실행 시 메모리 증가율 < 10%
- **복구 시간**: 크래시 발생 시 30초 이내 자동 재시작
- **Graceful shutdown**: 종료 시그널 수신 후 진행 중인 작업 완료 시간 < 60초

## 거버넌스

### 헌법 준수

- 본 헌법은 모든 개발 관행, 아키텍처 결정, 기능 구현보다 우선합니다
- 모든 Pull Request는 헌법 원칙 준수 여부를 검토해야 합니다
- 원칙 위반이 필요한 경우, 명확한 정당화와 대안 분석을 문서화해야 합니다

### 헌법 개정

- 헌법 개정은 프로젝트 리드의 승인이 필요합니다
- 개정 시 영향받는 모든 코드와 문서의 마이그레이션 계획을 포함해야 합니다
- 버전 관리:
  - **MAJOR**: 핵심 원칙 제거, 호환성 깨지는 변경
  - **MINOR**: 새로운 원칙/섹션 추가, 기존 원칙의 중요한 확장
  - **PATCH**: 문구 명확화, 오타 수정, 의미 변경 없는 개선

### 복잡성 정당화

- 새로운 기술 스택 도입, 아키텍처 패턴 추가 시 헌법 원칙과의 정렬을 입증해야 합니다
- "단순성" 원칙에 위배되는 복잡성 추가는 비즈니스 가치로 정당화되어야 합니다
- 런타임 개발 가이드는 `.specify/memory/guidance.md` (또는 해당 문서)를 참조합니다

### 준수 검토

- 분기별로 기존 코드베이스가 헌법 원칙을 준수하는지 검토합니다
- 원칙 위반 사항은 기술 부채로 등록하고 개선 계획을 수립합니다
