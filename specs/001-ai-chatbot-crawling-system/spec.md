## User Scenarios & Testing _(mandatory)_

### User Story 1 - AI 챗봇을 통한 크롤링 프로젝트 생성 (Priority: P1)

비개발자 사용자가 AI 챗봇과 자연어 대화를 통해 크롤링 프로젝트를 생성하고, 샘플 데이터를 검증한 후 프로젝트를 활성화할 수 있습니다.

**Why this priority**: 이 기능이 없으면 사용자는 프로젝트를 생성할 수 없으므로, DCS의 핵심 가치인 "비개발자도 사용 가능한 크롤링 서비스"의 근간이 됩니다. 이것만으로도 수동 크롤링 대비 큰 가치를 제공합니다.

**Independent Test**: 사용자가 챗봇과 대화하여 프로젝트를 생성하고, 샘플 크롤링 결과를 확인한 후 프로젝트를 활성화하면, 해당 프로젝트가 데이터베이스에 저장되고 대시보드에 표시되는지 확인할 수 있습니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 대시보드에 로그인한 상태, **When** "새 프로젝트 생성" 버튼을 클릭, **Then** AI 챗봇 대화창이 열리고 프로젝트명을 요청하는 메시지가 표시됨
2. **Given** 챗봇이 프로젝트명을 입력받은 상태, **When** 사용자가 "전국 지자체 사회복지기관"을 입력, **Then** 챗봇이 대상 URL을 요청함
3. **Given** 챗봇이 URL을 입력받은 상태, **When** 사용자가 특정 구청 URL을 입력, **Then** 챗봇이 수집할 첫 번째 데이터 필드명을 요청함
4. **Given** 챗봇이 필드명 "기관명"을 입력받은 상태, **When** AI가 HTML을 분석, **Then** 챗봇이 추천 CSS Selector와 샘플 데이터(예: "A복지관")를 제시하며 확인을 요청함
5. **Given** 사용자가 추천 Selector를 승인한 상태, **When** 사용자가 "추가 완료"를 입력, **Then** 챗봇이 수집 주기 설정을 요청함 (Cron 표현식 예제 제공)
6. **Given** 사용자가 "매월 1일 새벽 3시"를 선택한 상태, **When** 설정 완료, **Then** 챗봇이 구글챗 웹훅 URL 설정 의향을 묻음 (선택사항, 건너뛰기 가능)
7. **Given** 사용자가 웹훅 설정 단계, **When** 사용자가 구글챗 웹훅 URL을 입력하거나 건너뛰기, **Then** 챗봇이 샘플 크롤링 실행 의향을 묻음
8. **Given** 사용자가 샘플 크롤링 실행에 동의, **When** 샘플 크롤링 완료, **Then** 챗봇이 수집된 데이터 1~5건을 표시하며 정확성 확인 요청
9. **Given** 사용자가 데이터 정확성을 확정, **When** "확정" 버튼 클릭, **Then** 프로젝트가 활성(Active) 상태로 전환되고 스케줄링이 시작됨

### User Story 2 - 프로젝트 모니터링 및 관리 (Priority: P2)

사용자가 대시보드에서 모든 크롤링 프로젝트의 현황을 실시간으로 확인하고, 개별 프로젝트의 상세 정보, 수집 데이터, 에러 로그를 조회하며, 필요 시 재시도하거나 프로젝트를 일시정지/재개/삭제할 수 있습니다.

**Why this priority**: 프로젝트 생성(P1) 후 사용자는 크롤링 작업의 진행 상태를 파악하고 문제를 해결해야 합니다. 이 기능이 없으면 시스템이 백그라운드에서 무슨 일을 하는지 알 수 없어 신뢰도가 떨어집니다.

**Independent Test**: 사용자가 대시보드에 접속하여 프로젝트 목록을 확인하고, 특정 프로젝트를 클릭하여 상세 현황(성공/실패 건수, 최근 데이터, 에러 로그)을 조회하며, 실패한 작업을 재시도할 수 있는지 검증합니다.

**Acceptance Scenarios**:

1. **Given** 사용자가 대시보드에 접속한 상태, **When** 메인 화면 로드, **Then** 모든 프로젝트 목록이 표시됨 (프로젝트명, 상태, 마지막 실행일, 다음 실행일)
2. **Given** 프로젝트 목록이 표시된 상태, **When** 특정 프로젝트를 클릭, **Then** 프로젝트 상세 페이지로 이동하여 수집 현황이 시각화됨 (예: 256개 지자체별 테이블 또는 지도)
3. **Given** 프로젝트 상세 페이지에서, **When** 각 작업의 상태 표시, **Then** 성공/실패/대기 상태가 색상으로 구분되어 표시됨
4. **Given** 프로젝트 상세 페이지에서, **When** "최근 데이터" 탭 클릭, **Then** 최근 수집된 데이터 샘플 5~10건이 테이블 형태로 표시됨
5. **Given** 프로젝트 상세 페이지에서, **When** "에러 로그" 탭 클릭, **Then** 실패한 작업의 에러 메시지와 타임스탬프가 표시되며, 각 항목에 "재시도" 버튼이 있음
6. **Given** 에러 로그가 표시된 상태, **When** "재시도" 버튼 클릭, **Then** 해당 작업이 큐에 재등록되고, 상태가 "대기"로 변경됨
7. **Given** 프로젝트 상세 페이지에서, **When** "일시정지" 버튼 클릭, **Then** 스케줄링이 중단되고 프로젝트 상태가 "Paused"로 변경됨
8. **Given** 일시정지된 프로젝트, **When** "재개" 버튼 클릭, **Then** 스케줄링이 재개되고 상태가 "Active"로 변경됨
9. **Given** 프로젝트 상세 페이지에서, **When** "복제" 버튼 클릭, **Then** 기존 프로젝트의 모든 설정(URL, 필드, 스케줄, 웹훅)이 복사되어 새 프로젝트 생성 화면이 열리며, 프로젝트명만 변경하면 저장 가능

### User Story 3 - 예약된 자동 크롤링 실행 (Priority: P3)

시스템이 사용자가 설정한 스케줄(Cron 표현식)에 따라 백그라운드에서 자동으로 크롤링 작업을 실행하고, 결과를 저장하며, 실패 시 자동 재시도를 수행합니다.

**Why this priority**: 프로젝트 생성(P1)과 모니터링(P2)이 갖춰진 후, 자동화된 주기적 실행이 추가되면 완전한 자동 데이터 수집 시스템이 됩니다. 이 기능이 없어도 수동 실행으로 가치를 제공할 수 있지만, 자동화가 DCS의 핵심 효율성을 제공합니다.

**Independent Test**: 특정 시간(예: 매일 새벽 2시)으로 설정된 프로젝트가 해당 시간에 자동 실행되어 데이터가 수집되고, 대시보드에 새로운 실행 기록이 표시되는지 확인합니다. 타이머를 빠르게 설정(1분 후)하여 테스트 가능합니다.

**Acceptance Scenarios**:

1. **Given** "매일 새벽 2시" 스케줄로 설정된 활성 프로젝트, **When** 새벽 2시 도래, **Then** 스케줄러가 크롤링 작업을 작업 큐에 등록함
2. **Given** 작업 큐에 256개 지자체 크롤링 작업이 등록된 상태, **When** 실행 엔진이 작업을 가져옴, **Then** 개별 작업이 병렬로 실행됨 (최대 동시 실행 수: 256개)
3. **Given** 개별 크롤링 작업 실행 중, **When** 대상 웹페이지 접근 성공, **Then** 설정된 CSS Selector로 데이터를 추출하고 결과를 데이터베이스에 저장함 (projectId, run_timestamp 메타데이터 포함)
4. **Given** 개별 크롤링 작업 실행 중, **When** 네트워크 오류 발생 (타임아웃 등), **Then** 작업이 "실패" 상태로 기록되고, 30초 후 자동 재시도 큐에 등록됨 (최대 3회 재시도)
5. **Given** 3회 재시도 후에도 실패한 작업, **When** 최종 실패 확정, **Then** 에러 로그에 상세 메시지와 함께 기록되고, 사용자가 대시보드에서 확인 가능
6. **Given** 모든 작업 완료 후, **When** 크롤링 실행 종료, **Then** 프로젝트의 "마지막 실행일"이 업데이트되고, 성공/실패 통계가 대시보드에 반영됨

### User Story 4 - 수집 데이터 API 제공 (Priority: P4)

사용자가 프로젝트별 API 키를 발급받아, 외부 시스템에서 REST API를 통해 수집된 데이터를 조회할 수 있습니다.

**Why this priority**: 크롤링 데이터를 다른 시스템(데이터 분석, BI 도구 등)에서 활용하려면 API가 필요하지만, 대시보드에서 수동으로 데이터를 확인하는 것만으로도 기본 가치는 제공됩니다. 따라서 P4 우선순위입니다.

**Independent Test**: 사용자가 대시보드에서 API 키를 발급받고, 외부에서 curl 또는 Postman으로 GET 요청을 보내 데이터를 수신할 수 있는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 프로젝트 상세 페이지에 접속한 상태, **When** "API 키 발급" 버튼 클릭, **Then** 새로운 API 키가 생성되고 화면에 표시됨 (복사 버튼 제공)
2. **Given** API 키를 발급받은 상태, **When** 외부 시스템에서 `GET /api/v1/data/{projectId}` 요청 (Header: `X-API-Key: [발급받은 키]`), **Then** 최근 수집된 데이터가 JSON 형식으로 반환됨
3. **Given** API 요청 시, **When** 잘못된 API 키 사용, **Then** HTTP 401 Unauthorized 응답 반환
4. **Given** API 요청 시, **When** 존재하지 않는 projectId 사용, **Then** HTTP 404 Not Found 응답 반환
5. **Given** API 키를 발급받은 상태, **When** "API 키 재발급" 버튼 클릭, **Then** 기존 키가 무효화되고 새 키가 생성됨

---

### User Story 5 - 프로젝트 설정 수정 (Priority: P5)

사용자가 기존 프로젝트의 설정(수집 필드, 스케줄, 대상 URL 등)을 수정하고, 다시 샘플 크롤링으로 검증할 수 있습니다.

**Why this priority**: 대상 웹사이트 구조 변경 시 필요하지만, 새 프로젝트를 만드는 것으로 대체 가능하므로 가장 낮은 우선순위입니다.

**Independent Test**: 사용자가 프로젝트 상세 페이지에서 "설정 수정" 버튼을 클릭하여 챗봇을 다시 열고, 필드나 스케줄을 변경한 후 샘플 크롤링으로 검증하여 저장할 수 있는지 확인합니다.

**Acceptance Scenarios**:

1. **Given** 프로젝트 상세 페이지에 접속한 상태, **When** "설정 수정" 버튼 클릭, **Then** 챗봇이 열리고 현재 설정 내용이 표시됨
2. **Given** 챗봇이 현재 설정을 표시한 상태, **When** 사용자가 수집 필드를 추가/삭제/수정, **Then** AI가 새로운 CSS Selector를 추천함
3. **Given** 설정 변경 완료 후, **When** "샘플 크롤링 실행" 요청, **Then** 새 설정으로 샘플 데이터를 수집하여 표시함
4. **Given** 샘플 데이터 확인 후, **When** 사용자가 "저장" 클릭, **Then** 프로젝트 설정이 업데이트되고, 다음 스케줄 실행부터 새 설정 적용됨

### Edge Cases

- **대상 웹사이트가 응답하지 않는 경우**: 타임아웃(30초)이 발생하면 작업을 실패 처리하고, 자동 재시도 큐에 등록합니다. 3회 재시도 후에도 실패하면 에러 로그에 "웹사이트 접근 불가" 메시지를 기록합니다.
- **대상 웹사이트의 HTML 구조가 변경된 경우**: CSS Selector로 데이터를 찾지 못하면 빈 결과를 반환하고, 에러 로그에 "Selector 매칭 실패" 메시지를 기록합니다. 사용자는 대시보드에서 알림을 받고 프로젝트 설정을 수정할 수 있습니다.
- **동시에 256개 이상의 작업이 실행되는 경우**: 작업 큐 시스템이 작업을 순차적으로 처리하며, 동시 실행 수는 시스템 자원에 따라 자동 조절됩니다. 대기 중인 작업은 "대기" 상태로 표시됩니다.
- **여러 프로젝트의 스케줄이 동시에 실행되는 경우**: 스케줄 시각이 도래한 순서대로(선착순, FIFO) 작업 큐에 등록되며, 모든 프로젝트가 공정하게 처리됩니다. 우선순위는 없습니다.
- **사용자가 잘못된 URL을 입력한 경우**: 챗봇이 URL 형식을 검증하고, 잘못된 형식이면 "올바른 URL을 입력해주세요 (예: https://example.com)" 메시지를 표시합니다.
- **AI가 CSS Selector를 찾지 못한 경우**: 챗봇이 "죄송합니다. 해당 필드를 자동으로 찾지 못했습니다. 다른 필드명을 시도하거나, 고객지원에 문의해주세요"라고 안내합니다.
- **프로젝트 삭제 시 수집된 데이터 처리**: 사용자가 프로젝트 삭제를 요청하면, "수집된 데이터도 함께 삭제됩니다. 계속하시겠습니까?" 확인 메시지를 표시합니다. 확인 시 프로젝트 설정과 모든 수집 데이터를 삭제합니다.
- **프로젝트 복제 시 중복 이름**: 복제된 프로젝트 이름이 기존 프로젝트명과 동일하면, 시스템이 자동으로 " (복사본)" 또는 " (2)" 등을 추가하여 고유한 이름을 생성하고, 사용자가 수정할 수 있도록 합니다.
- **API 키 유출 시**: 사용자가 대시보드에서 "API 키 재발급"을 통해 즉시 기존 키를 무효화할 수 있습니다.
- **크롤링 대상 사이트가 봇 차단 메커니즘을 사용하는 경우**: 헤드리스 브라우저(Puppeteer/Playwright)를 사용하여 실제 브라우저처럼 동작하지만, CAPTCHA가 있는 경우 에러 로그에 "봇 차단 감지" 메시지를 기록하고 구글챗으로 알립니다.
- **구글챗 웹훅 알림 전송 실패 시**: 웹훅 URL이 잘못되었거나 구글챗 서비스 장애로 알림 전송이 실패해도, 크롤링 작업은 정상적으로 계속 진행되며 에러 로그에 "알림 전송 실패" 메시지를 기록합니다.

## Requirements _(mandatory)_

### Functional Requirements

**프로젝트 생성 및 설정**

- **FR-001**: 시스템은 사용자가 AI 챗봇과 자연어 대화를 통해 크롤링 프로젝트를 생성할 수 있어야 함
- **FR-002**: 챗봇은 사용자 입력(필드명)을 기반으로 대상 웹페이지의 HTML을 분석하여 CSS Selector를 자동으로 추천해야 함
- **FR-003**: 챗봇은 추천한 CSS Selector로 추출한 샘플 데이터를 사용자에게 제시하여 확인받아야 함
- **FR-004**: 사용자는 수집 주기를 자연어(예: "매일 아침 9시", "매월 1일")로 입력할 수 있어야 하며, 시스템이 이를 Cron 표현식으로 변환해야 함
- **FR-005**: 사용자는 샘플 크롤링 결과를 확인한 후 "확정"해야만 프로젝트가 활성화되어야 함
- **FR-006**: 각 프로젝트는 독립적인 데이터 스키마(수집 필드 구조)를 가져야 하며, 다른 프로젝트에 영향을 주지 않아야 함

**크롤링 실행**

- **FR-007**: 시스템은 설정된 스케줄(Cron 표현식)에 따라 자동으로 크롤링 작업을 실행해야 함
- **FR-008**: 여러 프로젝트의 스케줄이 동시에 실행될 경우, 선착순(FIFO) 방식으로 작업 큐에 등록되어야 함
- **FR-009**: 시스템은 대규모 작업(예: 256개 지자체)을 개별 작업 단위로 분리하여 병렬 처리해야 함
- **FR-010**: 각 크롤링 작업은 대상 URL에 접근하여 설정된 CSS Selector로 데이터를 추출하고, 결과를 저장해야 함
- **FR-011**: 시스템은 JavaScript로 동적 렌더링되는 웹페이지를 크롤링할 수 있어야 함
- **FR-012**: 크롤링 실패 시(네트워크 오류, 타임아웃 등) 시스템은 자동으로 최대 3회까지 재시도해야 함
- **FR-013**: 재시도 후에도 실패한 작업은 에러 로그에 상세 메시지와 함께 기록되어야 함

**데이터 저장 및 관리**

- **FR-014**: 수집된 데이터는 projectId와 run_timestamp 메타데이터를 포함하여 저장되어야 함
- **FR-015**: 시스템은 프로젝트별로 데이터를 격리하여 저장하고, 다른 프로젝트의 데이터에 접근할 수 없어야 함
- **FR-016**: 각 크롤링 실행의 성공/실패 상태가 개별적으로 추적되어야 함

**대시보드 및 모니터링**

- **FR-017**: 사용자는 대시보드에서 모든 프로젝트 목록을 확인할 수 있어야 함 (프로젝트명, 상태, 마지막 실행일, 다음 실행일)
- **FR-018**: 사용자는 프로젝트를 클릭하여 상세 현황을 확인할 수 있어야 함 (개별 작업의 성공/실패/대기 상태)
- **FR-019**: 대시보드는 최근 수집된 데이터 샘플(5~10건)을 표시해야 함
- **FR-020**: 대시보드는 실패한 작업의 에러 로그를 표시하고, 각 항목에 "재시도" 기능을 제공해야 함
- **FR-021**: 사용자는 프로젝트를 일시정지, 재개, 삭제, 복제할 수 있어야 함
- **FR-022**: 프로젝트 복제 시 기존 프로젝트의 모든 설정(대상 URL, 수집 필드, CSS Selector, 스케줄, 웹훅 URL)이 복사되어야 하며, 수집된 데이터는 복사되지 않아야 함

**알림**

- **FR-023**: 사용자는 프로젝트별로 구글챗(Google Chat) 웹훅 URL을 설정할 수 있어야 함
- **FR-024**: 시스템은 크롤링 실패 시 설정된 구글챗 웹훅으로 알림 메시지를 전송해야 함 (프로젝트명, 실패 원인, 실패 시각 포함)
- **FR-025**: 시스템은 크롤링 성공 완료 시 요약 정보를 구글챗 웹훅으로 전송해야 함 (프로젝트명, 수집 건수, 성공률)
- **FR-026**: 알림 전송 실패 시 시스템은 에러를 로깅하되, 크롤링 작업 자체에는 영향을 주지 않아야 함

**API 제공**

- **FR-027**: 사용자는 프로젝트별 API 키를 발급받을 수 있어야 함
- **FR-028**: 시스템은 API 키 인증을 통해 수집된 데이터를 REST API로 제공해야 함
- **FR-029**: API는 잘못된 인증 정보 사용 시 적절한 에러 응답(401 Unauthorized)을 반환해야 함

**보안 및 격리**

- **FR-030**: 시스템은 개인 계정 모델을 사용하며, 각 사용자는 자신이 생성한 프로젝트만 접근하고 수정할 수 있어야 함 (프로젝트 공유 또는 협업 기능 없음)
- **FR-031**: 크롤링 설정에 포함된 민감 정보(URL, 인증 정보, 웹훅 URL 등)는 암호화하여 저장해야 함
- **FR-032**: 특정 프로젝트의 크롤링 실패가 다른 프로젝트에 영향을 주지 않아야 함

### Key Entities

- **프로젝트 (Project)**: 크롤링 작업의 기본 단위. 속성: 프로젝트 ID, 프로젝트명, 생성일, 상태(Active/Paused/Inactive), 사용자 ID, 스케줄(Cron 표현식), 다음 실행 예정 시각
- **프로젝트 설정 (Project Configuration)**: 크롤링 방법 정의. 속성: 프로젝트 ID, 대상 URL 목록, 수집 필드 정의(필드명, CSS Selector), 타임아웃 설정, 재시도 설정, 구글챗 웹훅 URL (선택적)
- **크롤링 실행 (Crawling Run)**: 특정 시점에 실행된 크롤링 작업 그룹. 속성: 실행 ID, 프로젝트 ID, 실행 시작 시각, 실행 종료 시각, 총 작업 수, 성공 수, 실패 수
- **개별 작업 (Task)**: 단일 URL에 대한 크롤링 작업. 속성: 작업 ID, 실행 ID, 대상 URL, 상태(대기/실행중/성공/실패), 재시도 횟수, 에러 메시지
- **수집 데이터 (Collected Data)**: 크롤링으로 수집된 실제 데이터. 속성: 데이터 ID, 프로젝트 ID, 실행 ID, 수집 시각, 사용자 정의 필드들 (동적 스키마)
- **API 키 (API Key)**: 외부 API 접근 인증 정보. 속성: 키 ID, 프로젝트 ID, 키 값(해시), 발급일, 마지막 사용일, 상태(활성/비활성)
- **사용자 (User)**: 시스템 사용자 (개인 계정 모델, 팀 협업 없음). 속성: 사용자 ID, 이메일, 생성일, 소유한 프로젝트 목록 (관계)

## Success Criteria _(mandatory)_

### Measurable Outcomes

**사용성**

- **SC-001**: 비개발자 사용자가 AI 챗봇을 통해 크롤링 프로젝트를 생성하고 샘플 데이터를 확인하는 전체 과정을 5분 이내에 완료할 수 있음
- **SC-002**: 사용자의 90% 이상이 챗봇과의 대화만으로 CSS Selector나 Cron 표현식을 몰라도 프로젝트를 성공적으로 생성할 수 있음

**성능 및 확장성**

- **SC-003**: 시스템은 256개 이상의 개별 크롤링 작업을 동시에 처리할 수 있음
- **SC-004**: 대시보드의 프로젝트 목록 및 상세 현황 조회 응답 시간이 2초 이내임
- **SC-005**: 단일 페이지에 대한 샘플 크롤링 실행 시간이 10초 이내임
- **SC-006**: 시스템 전체 크롤링 작업 성공률이 95% 이상 유지됨 (일시적 네트워크 오류 제외)

**안정성 및 격리**

- **SC-007**: 특정 프로젝트의 크롤링 실패 시, 동시 실행 중인 다른 프로젝트에 영향을 주지 않음 (100% 격리)
- **SC-008**: 자동 재시도 메커니즘을 통해 일시적 네트워크 오류로 인한 실패의 70% 이상이 재시도에서 성공함

**자동화 효율성**

- **SC-009**: 스케줄된 크롤링 작업의 95% 이상이 정해진 시각으로부터 1분 이내에 시작됨
- **SC-010**: 사용자가 수동으로 데이터를 수집하는 것 대비, DCS를 사용하면 시간 소요가 90% 감소함 (예: 256개 지자체 데이터 수집 시 수동 8시간 → DCS 30분)

**데이터 정확성**

- **SC-011**: AI가 추천한 CSS Selector로 샘플 크롤링한 데이터의 정확도가 사용자 확정 기준 85% 이상임 (사용자가 첫 시도에서 확정하는 비율)

**비즈니스 가치**

- **SC-012**: DCS 도입 후, 크롤링 관련 사용자 문의 및 지원 요청이 50% 이상 감소함
- **SC-013**: 사용자의 80% 이상이 "DCS가 없었다면 불가능했을 작업을 수행할 수 있었다"고 응답함

## Assumptions

다음은 명세 작성 시 가정한 사항들입니다:

- **사용자 인증**: 사용자는 이메일/비밀번호 기반 인증으로 로그인합니다. OAuth2나 SSO는 향후 확장 가능하지만 초기 버전에서는 포함하지 않습니다.
- **사용자 역할**: 개인 계정 모델을 사용하며, 프로젝트 공유나 팀 협업 기능은 초기 버전에 포함되지 않습니다. 각 사용자는 자신의 프로젝트만 관리합니다.
- **데이터 보존 기간**: 수집된 데이터는 프로젝트가 삭제되기 전까지 무기한 보존되며, 사용자가 수동으로 삭제하지 않는 한 유지됩니다.
- **동시 사용자 수**: 초기 목표는 최대 100명의 동시 사용자를 지원하며, 사용자당 평균 5개의 프로젝트를 운영한다고 가정합니다.
- **크롤링 대상 제한**: 공개된 웹페이지만 크롤링 대상으로 하며, 로그인이 필요한 페이지는 1단계에서는 지원하지 않습니다 (향후 확장 가능).
- **봇 차단 대응**: 헤드리스 브라우저를 사용하지만, CAPTCHA가 있는 사이트는 크롤링이 불가능하며 에러로 처리합니다.
- **데이터 크기 제한**: 단일 크롤링 작업에서 수집하는 데이터는 최대 1MB로 제한하며, 이를 초과하면 경고 로그를 남기고 데이터를 잘라냅니다.
- **API Rate Limiting**: API 사용량 제한은 초기 버전에서는 적용하지 않으며, 필요 시 향후 추가합니다.
- **데이터 내보내기**: 대시보드에서 CSV/Excel 등으로 직접 내보내기 기능은 제공하지 않으며, 데이터는 API를 통해서만 조회 가능합니다.
- **다국어 지원**: 초기 버전은 한국어만 지원하며, 챗봇 인터페이스와 에러 메시지 모두 한국어로 제공됩니다.
