# 테스트 시나리오: DCS (동적 크롤링 서비스) 전체 시스템

**목적**: DCS 시스템의 모든 기능에 대한 통합 테스트 시나리오 및 검증 기준
**생성일**: 2025-01-18
**기능**: [spec.md](../spec.md)
**우선순위**: P1 (필수) → P5 (선택)

---

## 테스트 환경 준비사항

### 사전 조건

- [ ] ENV001 테스트 사용자 계정 생성 완료 (test@example.com)
- [ ] ENV002 테스트용 크롤링 대상 웹페이지 준비 (안정적 응답 보장)
- [ ] ENV003 구글챗 웹훅 테스트 URL 준비
- [ ] ENV004 데이터베이스 초기화 및 백업
- [ ] ENV005 테스트 환경 접속 확인 (프론트엔드, 백엔드, 데이터베이스)

### 테스트 데이터

- [ ] DATA001 샘플 URL 목록 준비 (정상 페이지, 느린 페이지, 오류 페이지)
- [ ] DATA002 예상 크롤링 결과 데이터셋 준비
- [ ] DATA003 다양한 Cron 표현식 테스트 케이스 준비

## P1: User Story 1 - AI 챗봇을 통한 크롤링 프로젝트 생성

### 1.1 챗봇 시작 및 프로젝트명 입력

- [ ] TS001 **Given** 사용자가 대시보드에 로그인한 상태, **When** "새 프로젝트 생성" 버튼을 클릭, **Then** AI 챗봇 대화창이 열리고 프로젝트명을 요청하는 메시지가 표시됨
  - 검증: 챗봇 UI가 화면에 정상 렌더링됨
  - 검증: "프로젝트 이름을 알려주세요" 메시지 출력됨
  - 검증: 입력창이 활성화되어 있음

- [ ] TS002 **Given** 챗봇이 프로젝트명을 입력받은 상태, **When** 사용자가 "전국 지자체 사회복지기관"을 입력, **Then** 챗봇이 대상 URL을 요청함
  - 검증: 입력한 프로젝트명이 챗봇 대화창에 표시됨
  - 검증: "데이터를 수집할 대표 URL 1개를 알려주세요" 메시지 출력됨

### 1.2 대상 URL 입력 및 검증

- [ ] TS003 **Given** 챗봇이 URL을 입력받은 상태, **When** 사용자가 특정 구청 URL을 입력, **Then** 챗봇이 수집할 첫 번째 데이터 필드명을 요청함
  - 검증: 입력한 URL이 올바른 형식인지 검증됨 (https:// 포함)
  - 검증: "수집할 첫 번째 데이터 필드명은 무엇인가요?" 메시지 출력됨

- [ ] TS004 **Edge Case** 사용자가 잘못된 URL 형식을 입력한 경우
  - **When** "example" (프로토콜 없음) 입력
  - **Then** "올바른 URL을 입력해주세요 (예: https://example.com)" 오류 메시지 표시됨

### 1.3 AI Selector 추천 및 확인

- [ ] TS005 **Given** 챗봇이 필드명 "기관명"을 입력받은 상태, **When** AI가 HTML을 분석, **Then** 챗봇이 추천 CSS Selector와 샘플 데이터(예: "A복지관")를 제시하며 확인을 요청함
  - 검증: AI가 3초 이내에 CSS Selector 추천 완료
  - 검증: 추천된 Selector (예: "td.name") 표시됨
  - 검증: 샘플 데이터 (예: "A복지관") 표시됨
  - 검증: "맞나요?" 확인 메시지와 "네/아니오" 버튼 표시됨

- [ ] TS006 **Edge Case** AI가 CSS Selector를 찾지 못한 경우
  - **When** 복잡한 JavaScript 렌더링 페이지 또는 비정형 HTML
  - **Then** "죄송합니다. 해당 필드를 자동으로 찾지 못했습니다. 다른 필드명을 시도하거나, 고객지원에 문의해주세요" 메시지 표시됨

- [ ] TS007 **Given** 사용자가 추천 Selector를 승인한 상태, **When** 사용자가 "추가 완료"를 입력, **Then** 챗봇이 수집 주기 설정을 요청함 (Cron 표현식 예제 제공)
  - 검증: 여러 필드 추가 후 "추가 완료" 입력 시 진행됨
  - 검증: Cron 표현식 예제 표시됨 ("매일 아침 9시", "매월 1일" 등)

### 1.4 스케줄 설정

- [ ] TS008 **Given** 사용자가 "매월 1일 새벽 3시"를 선택한 상태, **When** 설정 완료, **Then** 챗봇이 구글챗 웹훅 URL 설정 의향을 묻음 (선택사항, 건너뛰기 가능)
  - 검증: 사용자 입력이 올바른 Cron 표현식으로 변환됨 ("0 3 1 \* \*")
  - 검증: 변환된 Cron 표현식이 사용자에게 확인 메시지로 표시됨
  - 검증: "구글챗 웹훅 URL을 설정하시겠습니까? (선택사항)" 메시지 표시됨

### 1.5 웹훅 설정 (선택)

- [ ] TS009 **Given** 사용자가 웹훅 설정 단계, **When** 사용자가 구글챗 웹훅 URL을 입력하거나 건너뛰기, **Then** 챗봇이 샘플 크롤링 실행 의향을 묻음
  - 검증 (입력 시): 웹훅 URL 형식 검증 (https://chat.googleapis.com/...)
  - 검증 (건너뛰기 시): 웹훅 URL 없이 진행됨
  - 검증: "설정이 완료되었습니다. 샘플 크롤링을 실행해볼까요?" 메시지 표시됨

### 1.6 샘플 크롤링 실행

- [ ] TS010 **Given** 사용자가 샘플 크롤링 실행에 동의, **When** 샘플 크롤링 완료, **Then** 챗봇이 수집된 데이터 1~5건을 표시하며 정확성 확인 요청
  - 검증: 샘플 크롤링이 10초 이내에 완료됨 (FR 요구사항: SC-005)
  - 검증: 수집된 데이터 1~5건이 테이블 형식으로 표시됨
  - 검증: 각 필드의 데이터가 올바르게 추출되었는지 시각적으로 확인 가능
  - 검증: "데이터가 정확한가요?" 메시지와 "확정/수정" 버튼 표시됨

### 1.7 프로젝트 확정 및 활성화

- [ ] TS011 **Given** 사용자가 데이터 정확성을 확정, **When** "확정" 버튼 클릭, **Then** 프로젝트가 활성(Active) 상태로 전환되고 스케줄링이 시작됨
  - 검증: 프로젝트가 데이터베이스에 저장됨 (status="Active")
  - 검증: "프로젝트가 활성화되었습니다. 매월 1일 새벽 3시에 자동 실행됩니다" 성공 메시지 표시됨
  - 검증: 대시보드 프로젝트 목록에 새 프로젝트가 표시됨
  - 검증: 다음 실행 예정 시각이 올바르게 계산되어 표시됨

## P2: User Story 2 - 프로젝트 모니터링 및 관리

### 2.1 프로젝트 목록 조회

- [ ] TS012 **Given** 사용자가 대시보드에 접속한 상태, **When** 메인 화면 로드, **Then** 모든 프로젝트 목록이 표시됨 (프로젝트명, 상태, 마지막 실행일, 다음 실행일)
  - 검증: 프로젝트 목록이 2초 이내에 로드됨 (FR 요구사항: SC-004)
  - 검증: 각 프로젝트의 이름, 상태(Active/Paused), 마지막 실행일, 다음 실행일이 표시됨
  - 검증: 프로젝트가 없는 경우 "새 프로젝트를 생성하세요" 안내 메시지 표시됨

### 2.2 프로젝트 상세 현황 조회

- [ ] TS013 **Given** 프로젝트 목록이 표시된 상태, **When** 특정 프로젝트를 클릭, **Then** 프로젝트 상세 페이지로 이동하여 수집 현황이 시각화됨 (예: 256개 지자체별 테이블 또는 지도)
  - 검증: 프로젝트 상세 페이지가 2초 이내에 로드됨
  - 검증: 프로젝트 기본 정보 표시 (프로젝트명, 생성일, 스케줄, 상태)
  - 검증: 수집 현황이 시각적으로 표시됨 (테이블, 차트, 또는 지도)

- [ ] TS014 **Given** 프로젝트 상세 페이지에서, **When** 각 작업의 상태 표시, **Then** 성공/실패/대기 상태가 색상으로 구분되어 표시됨
  - 검증: 성공 작업 = 녹색, 실패 작업 = 빨간색, 대기 작업 = 노란색 등 시각적 구분
  - 검증: 각 상태별 건수가 집계되어 표시됨 (예: 성공 250건, 실패 6건)

### 2.3 최근 데이터 조회

- [ ] TS015 **Given** 프로젝트 상세 페이지에서, **When** "최근 데이터" 탭 클릭, **Then** 최근 수집된 데이터 샘플 5~10건이 테이블 형태로 표시됨
  - 검증: 최근 데이터 5~10건이 테이블로 표시됨
  - 검증: 각 레코드의 수집 시각(timestamp)이 표시됨
  - 검증: 프로젝트에서 정의한 모든 필드가 컬럼으로 표시됨

### 2.4 에러 로그 조회 및 재시도

- [ ] TS016 **Given** 프로젝트 상세 페이지에서, **When** "에러 로그" 탭 클릭, **Then** 실패한 작업의 에러 메시지와 타임스탬프가 표시되며, 각 항목에 "재시도" 버튼이 있음
  - 검증: 실패한 작업 목록이 최신순으로 표시됨
  - 검증: 각 항목에 대상 URL, 에러 메시지, 실패 시각, 재시도 횟수가 표시됨
  - 검증: 각 항목에 "재시도" 버튼이 활성화되어 있음

- [ ] TS017 **Given** 에러 로그가 표시된 상태, **When** "재시도" 버튼 클릭, **Then** 해당 작업이 큐에 재등록되고, 상태가 "대기"로 변경됨
  - 검증: "재시도" 버튼 클릭 시 확인 팝업 표시됨
  - 검증: 작업이 큐에 재등록됨 (작업 상태 = "대기")
  - 검증: 재시도 횟수가 증가됨
  - 검증: "재시도가 예약되었습니다" 성공 메시지 표시됨

### 2.5 프로젝트 상태 관리

- [ ] TS018 **Given** 프로젝트 상세 페이지에서, **When** "일시정지" 버튼 클릭, **Then** 스케줄링이 중단되고 프로젝트 상태가 "Paused"로 변경됨
  - 검증: "일시정지하시겠습니까?" 확인 팝업 표시됨
  - 검증: 프로젝트 상태가 "Paused"로 변경됨
  - 검증: 스케줄링이 중단됨 (다음 실행 예정 시각 = null)
  - 검증: "프로젝트가 일시정지되었습니다" 성공 메시지 표시됨

- [ ] TS019 **Given** 일시정지된 프로젝트, **When** "재개" 버튼 클릭, **Then** 스케줄링이 재개되고 상태가 "Active"로 변경됨
  - 검증: 프로젝트 상태가 "Active"로 변경됨
  - 검증: 다음 실행 예정 시각이 재계산되어 표시됨
  - 검증: "프로젝트가 재개되었습니다" 성공 메시지 표시됨

### 2.6 프로젝트 복제

- [ ] TS020 **Given** 프로젝트 상세 페이지에서, **When** "복제" 버튼 클릭, **Then** 기존 프로젝트의 모든 설정(URL, 필드, 스케줄, 웹훅)이 복사되어 새 프로젝트 생성 화면이 열리며, 프로젝트명만 변경하면 저장 가능
  - 검증: 챗봇이 열리며 기존 설정이 미리 입력되어 있음
  - 검증: 프로젝트명 필드만 비어있고 편집 가능함
  - 검증: 대상 URL, 필드 정의, 스케줄, 웹훅 URL이 원본과 동일하게 복사됨
  - 검증: 수집된 데이터는 복사되지 않음

- [ ] TS021 **Edge Case** 프로젝트 복제 시 중복 이름
  - **When** 복제 시 프로젝트명을 원본과 동일하게 입력
  - **Then** 시스템이 자동으로 " (복사본)" 또는 " (2)" 추가
  - 검증: 고유한 프로젝트명으로 저장됨

## P3: User Story 3 - 예약된 자동 크롤링 실행

### 3.1 스케줄 트리거

- [ ] TS022 **Given** "매일 새벽 2시" 스케줄로 설정된 활성 프로젝트, **When** 새벽 2시 도래, **Then** 스케줄러가 크롤링 작업을 작업 큐에 등록함
  - 검증: 스케줄 시각으로부터 1분 이내에 작업이 큐에 등록됨 (FR 요구사항: SC-009)
  - 검증: 프로젝트의 "마지막 실행일"이 업데이트됨
  - 검증: 크롤링 Run 레코드가 데이터베이스에 생성됨 (status="Running")

- [ ] TS023 **Edge Case** 여러 프로젝트의 스케줄이 동시에 실행되는 경우
  - **When** 5개 프로젝트가 모두 새벽 2시로 스케줄됨
  - **Then** 선착순(FIFO) 방식으로 작업 큐에 등록됨
  - 검증: 모든 프로젝트가 공정하게 처리됨
  - 검증: 우선순위 없이 도착 순서대로 실행됨

### 3.2 병렬 크롤링 실행

- [ ] TS024 **Given** 작업 큐에 256개 지자체 크롤링 작업이 등록된 상태, **When** 실행 엔진이 작업을 가져옴, **Then** 개별 작업이 병렬로 실행됨 (최대 동시 실행 수: 256개)
  - 검증: 시스템이 256개 이상의 작업을 동시 처리할 수 있음 (FR 요구사항: SC-003)
  - 검증: 각 작업의 상태가 "대기" → "실행중" → "성공/실패"로 변경됨
  - 검증: 작업 간 간섭이 없음 (격리 보장)

- [ ] TS025 **Edge Case** 동시에 256개 이상의 작업이 실행되는 경우
  - **When** 500개 작업이 동시에 큐에 등록됨
  - **Then** 시스템 자원에 따라 동시 실행 수 자동 조절됨
  - 검증: 대기 중인 작업은 "대기" 상태로 표시됨
  - 검증: 리소스가 확보되면 대기 작업이 순차 실행됨

### 3.3 데이터 수집 및 저장

- [ ] TS026 **Given** 개별 크롤링 작업 실행 중, **When** 대상 웹페이지 접근 성공, **Then** 설정된 CSS Selector로 데이터를 추출하고 결과를 데이터베이스에 저장함 (projectId, run_timestamp 메타데이터 포함)
  - 검증: CSS Selector로 데이터 정확하게 추출됨
  - 검증: 추출된 데이터가 데이터베이스에 저장됨
  - 검증: projectId, runId, timestamp 메타데이터가 포함됨
  - 검증: 작업 상태가 "성공"으로 변경됨

### 3.4 오류 처리 및 재시도

- [ ] TS027 **Given** 개별 크롤링 작업 실행 중, **When** 네트워크 오류 발생 (타임아웃 등), **Then** 작업이 "실패" 상태로 기록되고, 30초 후 자동 재시도 큐에 등록됨 (최대 3회 재시도)
  - 검증: 타임아웃 설정(30초) 적용됨
  - 검증: 네트워크 오류 시 작업이 "실패" 상태로 변경됨
  - 검증: 30초 후 자동 재시도 큐에 등록됨
  - 검증: 재시도 횟수가 증가됨 (max 3회)

- [ ] TS028 **Given** 3회 재시도 후에도 실패한 작업, **When** 최종 실패 확정, **Then** 에러 로그에 상세 메시지와 함께 기록되고, 사용자가 대시보드에서 확인 가능
  - 검증: 재시도 3회 모두 실패 시 최종 "실패" 상태로 확정됨
  - 검증: 에러 로그에 실패 원인, 재시도 횟수, 타임스탬프 기록됨
  - 검증: 대시보드 에러 로그 탭에서 확인 가능함
  - 검증: 자동 재시도 메커니즘의 70% 이상이 성공함 (FR 요구사항: SC-008)

- [ ] TS029 **Edge Case** 대상 웹사이트가 응답하지 않는 경우
  - **When** 대상 URL이 30초 이내 응답하지 않음
  - **Then** 타임아웃 발생 및 실패 처리
  - 검증: "웹사이트 접근 불가" 에러 메시지 기록됨
  - 검증: 자동 재시도 3회 시도됨

- [ ] TS030 **Edge Case** 대상 웹사이트의 HTML 구조가 변경된 경우
  - **When** CSS Selector로 데이터를 찾지 못함
  - **Then** 빈 결과 반환 및 에러 로그 기록
  - 검증: "Selector 매칭 실패" 에러 메시지 기록됨
  - 검증: 사용자가 대시보드에서 알림 확인 가능
  - 검증: 프로젝트 설정 수정 가능함

### 3.5 실행 완료 및 통계

- [ ] TS031 **Given** 모든 작업 완료 후, **When** 크롤링 실행 종료, **Then** 프로젝트의 "마지막 실행일"이 업데이트되고, 성공/실패 통계가 대시보드에 반영됨
  - 검증: Run 레코드의 status가 "Completed"로 변경됨
  - 검증: 총 작업 수, 성공 수, 실패 수가 정확히 집계됨
  - 검증: 프로젝트의 "마지막 실행일"이 현재 시각으로 업데이트됨
  - 검증: 다음 실행 예정 시각이 Cron 표현식 기반으로 재계산됨
  - 검증: 전체 크롤링 성공률이 95% 이상 유지됨 (FR 요구사항: SC-006)

### 3.6 프로젝트 격리

  - **When** 프로젝트 A가 오류로 실패
  - **Then** 동시 실행 중인 프로젝트 B는 정상 진행됨
  - 검증: 100% 격리 보장 (FR 요구사항: SC-007)

## P4: User Story 4 - 수집 데이터 API 제공

### 4.1 API 키 발급

- [ ] TS033 **Given** 프로젝트 상세 페이지에 접속한 상태, **When** "API 키 발급" 버튼 클릭, **Then** 새로운 API 키가 생성되고 화면에 표시됨 (복사 버튼 제공)
  - 검증: 고유한 API 키가 생성됨 (최소 32자 이상)
  - 검증: API 키가 화면에 표시되고 복사 버튼이 제공됨
  - 검증: API 키가 데이터베이스에 해시되어 저장됨
  - 검증: "API 키가 발급되었습니다. 안전하게 보관하세요" 안내 메시지 표시됨

### 4.2 API 데이터 조회 (성공)

- [ ] TS034 **Given** API 키를 발급받은 상태, **When** 외부 시스템에서 `GET /api/v1/data/{projectId}` 요청 (Header: `X-API-Key: [발급받은 키]`), **Then** 최근 수집된 데이터가 JSON 형식으로 반환됨
  - 검증: HTTP 200 OK 응답
  - 검증: JSON 형식으로 데이터 반환됨
  - 검증: Response 구조: `{ "status": "success", "last_updated": "...", "data": [...] }`
  - 검증: 프로젝트의 모든 수집 필드가 포함됨
  - 검증: 최근 수집된 데이터가 시간순으로 정렬되어 반환됨

### 4.3 API 인증 실패

- [ ] TS035 **Given** API 요청 시, **When** 잘못된 API 키 사용, **Then** HTTP 401 Unauthorized 응답 반환
  - 검증: HTTP 401 Unauthorized 응답
  - 검증: 에러 메시지: `{ "error": "Invalid API Key" }`
  - 검증: 데이터가 반환되지 않음

### 4.4 API 리소스 없음

- [ ] TS036 **Given** API 요청 시, **When** 존재하지 않는 projectId 사용, **Then** HTTP 404 Not Found 응답 반환
  - 검증: HTTP 404 Not Found 응답
  - 검증: 에러 메시지: `{ "error": "Project not found" }`

### 4.5 API 키 재발급

- [ ] TS037 **Given** API 키를 발급받은 상태, **When** "API 키 재발급" 버튼 클릭, **Then** 기존 키가 무효화되고 새 키가 생성됨
  - 검증: "기존 API 키가 무효화됩니다. 계속하시겠습니까?" 확인 팝업 표시됨
  - 검증: 기존 API 키의 상태가 "비활성"으로 변경됨
  - 검증: 새로운 API 키가 생성되어 화면에 표시됨
  - 검증: 기존 API 키로 요청 시 401 에러 반환됨

- [ ] TS038 **Edge Case** API 키 유출 시 즉시 무효화 가능
  - **When** 사용자가 "API 키 재발급" 클릭
  - **Then** 기존 키가 즉시 무효화됨
  - 검증: 재발급 후 1초 이내에 기존 키 사용 불가
