## 사용자 시나리오 및 테스트 _(필수)_

### User Story 1 - 데몬 프로세스 기반 크롤링 실행 (우선순위: P1)

시스템 운영자는 크롤링 작업을 백그라운드 데몬 프로세스로 실행하여, 서버 재부팅이나 일시적인 장애에도 자동으로 복구되는 안정적인 크롤링 환경을 구축할 수 있습니다.

**우선순위 이유**: 데몬 환경에서의 안정적 운영은 시스템의 핵심 요구사항이며, 모든 다른 기능의 기반이 됩니다.

**독립 테스트**: 데몬 프로세스를 시작하고, 수동으로 프로세스를 종료한 후 자동 재시작되는지 확인하여 독립적으로 검증 가능합니다.

**수락 시나리오**:

1. **Given** 크롤링 작업이 설정되어 있을 때, **When** 데몬 프로세스를 시작하면, **Then** 백그라운드에서 크롤링 작업이 실행되고 프로세스 상태가 "실행 중"으로 표시됨
2. **Given** 데몬 프로세스가 실행 중일 때, **When** 프로세스가 예기치 않게 종료되면, **Then** 30초 이내에 자동으로 재시작되고 중단된 작업이 재개됨
3. **Given** 데몬 프로세스가 실행 중일 때, **When** 정상 종료 신호(SIGTERM)를 보내면, **Then** 진행 중인 작업을 완료한 후 60초 이내에 안전하게 종료됨
4. **Given** 데몬 프로세스가 24시간 이상 실행되었을 때, **When** 메모리 사용량을 확인하면, **Then** 초기 메모리 사용량 대비 10% 이상 증가하지 않음

### User Story 2 - 다양한 크롤링 환경 지원 (우선순위: P2)

사용자는 정적 HTML 페이지부터 JavaScript로 렌더링되는 SPA, 인증이 필요한 페이지, API 기반 데이터 수집까지 다양한 크롤링 환경을 하나의 시스템에서 처리할 수 있습니다.

**우선순위 이유**: 실제 크롤링 요구사항은 매우 다양하므로, 여러 환경을 지원하는 것이 시스템의 범용성을 확보하는 핵심입니다.

**독립 테스트**: 각 크롤링 환경(정적/동적/인증/API)별로 샘플 데이터를 수집하여 독립적으로 검증 가능합니다.

**수락 시나리오**:

1. **Given** 정적 HTML 페이지 URL이 제공되었을 때, **When** 크롤링을 실행하면, **Then** HTML 파서를 사용하여 10초 이내에 데이터를 수집함
2. **Given** JavaScript 렌더링이 필요한 SPA 페이지 URL이 제공되었을 때, **When** 크롤링을 실행하면, **Then** 헤드리스 브라우저를 사용하여 동적 콘텐츠를 수집함
3. **Given** 인증 정보(사용자명, 비밀번호)가 제공되었을 때, **When** 인증이 필요한 페이지를 크롤링하면, **Then** 자동으로 로그인한 후 데이터를 수집함
4. **Given** API 엔드포인트 URL이 제공되었을 때, **When** API 기반 크롤링을 실행하면, **Then** JSON/XML 응답을 파싱하여 데이터를 수집함
5. **Given** 파일 다운로드 URL(PDF, CSV 등)이 제공되었을 때, **When** 크롤링을 실행하면, **Then** 파일을 다운로드하고 메타데이터를 저장함

### User Story 3 - 실시간 헬스 체크 및 모니터링 (우선순위: P3)

시스템 운영자는 데몬 프로세스의 상태(uptime, 메모리, CPU, 작업 큐 길이)를 실시간으로 모니터링하고, 문제 발생 시 즉시 알림을 받을 수 있습니다.

**우선순위 이유**: 안정적인 운영을 위해 필요하지만, 데몬 실행과 크롤링 기능이 먼저 구현되어야 의미가 있습니다.

**독립 테스트**: 헬스 체크 엔드포인트를 호출하여 프로세스 상태 정보를 확인함으로써 독립적으로 검증 가능합니다.

**수락 시나리오**:

1. **Given** 데몬 프로세스가 실행 중일 때, **When** 헬스 체크 엔드포인트를 호출하면, **Then** 프로세스 상태(uptime, 메모리, CPU, 작업 큐 길이)가 2초 이내에 반환됨
2. **Given** 데몬 프로세스의 메모리 사용량이 임계값(80%)을 초과했을 때, **When** 모니터링 시스템이 확인하면, **Then** 운영자에게 알림이 전송됨
3. **Given** 작업 큐에 처리되지 않은 작업이 100개 이상 쌓였을 때, **When** 모니터링 시스템이 확인하면, **Then** 대기 시간 경고가 표시됨
4. **Given** 반복적으로 실패하는 작업이 Dead Letter Queue에 쌓였을 때, **When** 모니터링 대시보드를 확인하면, **Then** 실패한 작업 목록과 에러 메시지가 표시됨

### 엣지 케이스

- 데몬 프로세스가 연속해서 5회 이상 크래시하는 경우 어떻게 처리하나요?
- 크롤링 대상 서버가 응답하지 않거나 타임아웃이 발생하는 경우 어떻게 처리하나요?
- 동시에 256개 이상의 크롤링 작업이 요청되었을 때 시스템이 어떻게 대응하나요?
- 디스크 공간이 부족하여 로그 파일이나 데이터를 저장할 수 없는 경우 어떻게 처리하나요?
- Graceful shutdown 시간(60초)을 초과하는 긴 작업이 실행 중인 경우 어떻게 처리하나요?

## 요구사항 _(필수)_

### 기능 요구사항

- **FR-001**: 시스템은 백그라운드 데몬 프로세스로 실행되어야 함
- **FR-002**: 시스템은 프로세스 크래시 시 30초 이내에 자동으로 재시작되어야 함
- **FR-003**: 시스템은 정상 종료 신호(SIGTERM, SIGINT) 수신 시 진행 중인 작업을 완료한 후 60초 이내에 안전하게 종료되어야 함
- **FR-004**: 시스템은 정적 HTML 페이지, JavaScript 렌더링 페이지(SPA), 인증 필요 페이지, API 엔드포인트, 파일 다운로드를 지원해야 함
- **FR-005**: 시스템은 프로젝트별로 독립적인 크롤링 작업을 격리하여 실행해야 함 (한 프로젝트의 실패가 다른 프로젝트에 영향을 주지 않음)
- **FR-006**: 시스템은 최소 256개의 동시 크롤링 작업을 처리할 수 있어야 함
- **FR-007**: 시스템은 크롤링 실패 시 자동 재시도 메커니즘을 제공해야 함
- **FR-008**: 시스템은 반복 실패 작업을 Dead Letter Queue에 별도 관리해야 함
- **FR-009**: 시스템은 헬스 체크 엔드포인트를 통해 프로세스 상태(uptime, 메모리, CPU, 작업 큐 길이)를 제공해야 함
- **FR-010**: 시스템은 구조화된 로그를 생성하고, 로그 파일 크기 제한 및 자동 순환(rotation)을 지원해야 함
- **FR-011**: 시스템은 중복 실행을 방지하기 위한 PID 파일 관리를 제공해야 함
- **FR-012**: 시스템은 24시간 이상 실행 시 메모리 증가율이 10% 이하로 유지되어야 함 (메모리 누수 방지)

### 주요 엔티티

- **크롤링 프로젝트**: 크롤링 대상 URL, 수집할 데이터 필드, 스케줄 정보, 크롤링 전략(정적/동적/API 등)을 포함하는 독립적인 작업 단위
- **크롤링 작업(Job)**: 특정 시점에 실행되는 단일 크롤링 실행, 상태(대기/실행중/성공/실패), 시작 시간, 종료 시간, 수집된 데이터 건수 등을 포함
- **수집 데이터**: 프로젝트별로 정의된 스키마에 따라 수집된 데이터, projectId, run_timestamp 메타데이터 포함
- **데몬 프로세스**: 백그라운드에서 실행되는 메인 프로세스, PID, uptime, 메모리 사용량, CPU 사용률 정보 포함
- **작업 큐**: 실행 대기 중인 크롤링 작업의 대기열, FIFO 방식으로 처리
- **Dead Letter Queue**: 반복적으로 실패한 작업의 별도 대기열, 에러 메시지 및 재시도 횟수 포함

## 성공 기준 _(필수)_

### 측정 가능한 결과

- **SC-001**: 데몬 프로세스의 월간 Uptime이 99.9% 이상 유지됨 (최대 43분 다운타임)
- **SC-002**: 프로세스 크래시 발생 시 30초 이내에 자동 재시작됨
- **SC-003**: 24시간 이상 연속 실행 시 메모리 증가율이 10% 이하로 유지됨
- **SC-004**: 정상 종료 신호 수신 후 진행 중인 작업을 완료하고 60초 이내에 종료됨
- **SC-005**: 최소 256개의 동시 크롤링 작업을 성공적으로 처리함
- **SC-006**: 전체 크롤링 작업의 성공률이 95% 이상임
- **SC-007**: 헬스 체크 엔드포인트가 2초 이내에 프로세스 상태 정보를 반환함
- **SC-008**: 사용자가 5가지 크롤링 환경(정적 HTML, SPA, 인증, API, 파일)에서 데이터를 성공적으로 수집함

## 가정 사항

- 데몬 프로세스 관리 도구로 systemd, supervisor, 또는 PM2 같은 표준 도구를 사용할 수 있다고 가정합니다
- 크롤링 대상 서버는 표준적인 HTTP/HTTPS 프로토콜을 사용한다고 가정합니다
- 시스템 리소스(메모리, CPU, 디스크)는 256개 동시 작업을 처리하기에 충분하다고 가정합니다
- 로그 저장 공간은 충분하며, 오래된 로그는 자동으로 삭제되거나 아카이빙된다고 가정합니다
- 네트워크 연결은 일시적인 장애가 발생할 수 있으므로 재시도 메커니즘이 필요하다고 가정합니다

## 범위

### 포함

- 데몬 프로세스 기반 실행 및 자동 재시작
- 다양한 크롤링 환경 지원 (정적/동적/인증/API/파일)
- Graceful shutdown 및 리소스 관리
- 헬스 체크 및 프로세스 모니터링
- 작업 큐 및 Dead Letter Queue 관리
- 구조화된 로깅 및 로그 로테이션
